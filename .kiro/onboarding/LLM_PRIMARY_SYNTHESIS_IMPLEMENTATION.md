# LLM-Primary Steering Synthesis Pipeline - Implementation Summary

**Version**: 3.0.0  
**Status**: ✅ Complete  
**Date**: February 25, 2026

---

## Overview

This document summarizes the implementation of the LLM-Primary Steering Synthesis pipeline, a fundamental architectural refactor that replaces the regex-based `TemplatePopulator` fallback system with an LLM-first approach for generating steering files.

### Problem Statement

The previous pipeline had an inverted architecture:
- `TemplatePopulator` was the de-facto primary path, producing low-quality output (unfilled placeholders, copy-pasted paragraphs, content bleeding across sections)
- LLM was an optional afterthought, only used when explicitly configured
- No structured context preparation or token budget enforcement
- No validation of LLM outputs for hallucinations or duplicates

### Solution

The new pipeline inverts this architecture:
- **Every steering file is generated by an LLM call**
- Python code is responsible only for:
  - Preparing structured context with token budgets
  - Validating LLM outputs
  - Writing validated output atomically to disk
- `TemplatePopulator` is removed from the primary generation path entirely

## Architecture

### New Components

| Component | Responsibility | File |
|-----------|---------------|------|
| **InputResolver** | Determines use case, resolves source folder path | `input_resolver.py` |
| **CodeAnalysisFacts** | Structured JSON output from CodeAnalyzer (≤2,000 tokens) | `models.py` |
| **DocumentParser** | Bounded document parsing (enforces source folder scope) | `parsers/orchestrator.py` |
| **DeltaAnalyzer** | Three-way diff: docs vs code vs steering | `delta_analyzer.py` |
| **ContextAssembler** | Token-budgeted context per template (≤8,000 tokens) | `context_assembler.py` |
| **PromptBuilder** | Structured LLM prompts with instructions | `prompt_builder.py` |
| **SteeringFileGenerator** | Transactional orchestration of all 8 files | `steering_file_generator.py` |

### Pipeline Flow

```
InputResolver → CodeAnalyzer → DocumentParser → DeltaAnalyzer
    ↓
ContextAssembler (per template, token-budgeted)
    ↓
PromptBuilder (system + user prompts)
    ↓
LLMProvider (8 calls, one per template)
    ↓
Validation (hallucination detection + duplicate checking)
    ↓
Atomic Write (all 8 files or none)
```

### Generation Order

Files are generated sequentially to provide cross-file context via rolling summaries:

1. `project-vision.md`
2. `tech-stack.md`
3. `architecture.md`
4. `conventions.md`
5. `agents.md`
6. `workflows.md`
7. `security.md`
8. `testing.md`

## Key Features

### 1. Use Case Determination

**InputResolver** automatically determines the workflow use case:

| Source Docs | Codebase | Existing Steering | Use Case |
|-------------|----------|-------------------|----------|
| Yes | No | No | `new_from_docs` |
| No | Yes | No | `reverse_engineer` |
| Yes | Yes | Yes | `drift_correction` |
| Any | Any | Broken/partial | `error_recovery` |
| Yes (with intent.md) | Any | Any | `pivot` |

### 2. Token Budget Enforcement

**ContextAssembler** enforces strict per-template token budgets:

- **Total Budget**: 8,000 tokens per template
- **Source Docs**: 4,000 tokens (50%)
- **Code Facts**: 2,000 tokens (25%)
- **Existing Steering**: 1,000 tokens (12.5%)
- **Previously Generated**: 1,000 tokens (12.5%)

**Strategy**:
1. **Primary**: Keyword-based relevance filtering (reduces input before truncation)
2. **Secondary**: Token budget allocation
3. **Last Resort**: Simple truncation with `[TRUNCATED]` markers

### 3. Hallucination Detection

**SteeringFileGenerator** validates LLM outputs for contradictions:

- **Database name**: Must match `CodeAnalysisFacts.database`
- **Backend framework**: Must match `CodeAnalysisFacts.frameworks`
- **Duplicate paragraphs**: Detects verbatim duplication across sections

**On hallucination error**: Abort entire transaction immediately (no retry)

### 4. Retry Logic

**Empty/malformed response handling**:
- First attempt: Full prompt with all context
- If empty/malformed: Retry once with simplified prompt
- If still empty/malformed: Fail and abort

**Never retry on**: Hallucination errors (these indicate incorrect output, not formatting issues)

### 5. Atomic Transactions

**All-or-nothing file writing**:
- Generate all 8 files in memory
- Validate each draft
- If any validation fails: Discard all drafts, write zero files
- If all pass: Write all 8 files atomically

## Implementation Details

### CodeAnalysisFacts Structure

Replaces prose `to_summary()` with structured JSON:

```python
@dataclass
class CodeAnalysisFacts:
    primary_language: str
    frameworks: List[str]
    dependencies: List[Dependency]
    architecture_pattern: str
    has_tests: bool
    test_framework: Optional[str]
    api_type: Optional[str]  # "REST", "MCP", "CLI", None
    database: Optional[str]
    entry_points: List[str]
    naming_conventions: NamingConventions
    directory_structure: str
    
    def to_json_dict(self) -> Dict[str, Any]:
        """Guarantees ≤2,000 tokens via truncation if needed"""
```

### Prompt Structure

**System Prompt** instructs the LLM to:
- Fill every section independently
- Write `N/A` for absent information
- Write `[NOT FOUND]` for expected-but-absent fields
- Never repeat content across sections
- Output only final Markdown (no preamble)

**User Prompt** includes:
- Template section schema
- Source document content (filtered by relevance)
- Code facts (JSON)
- Existing steering content (truncated)
- Delta report (for drift_correction/update use cases)
- User intent (if provided)
- Previously generated file summaries

### Validation Rules

**Hallucination Detection** (deterministic string matching):
- If draft mentions database name that contradicts `CodeAnalysisFacts.database` → Error
- If draft mentions framework that contradicts `CodeAnalysisFacts.frameworks` → Error

**Duplicate Paragraph Detection**:
- Split draft into paragraphs (≥80 characters, separated by `\n\n`)
- Check for verbatim duplicates across sections
- If found → Error

## Migration Guide

### For Users

**No breaking changes** for CLI users:
- `hiveforge steering init` works exactly as before
- `hiveforge steering update` works exactly as before
- LLM configuration remains the same

**New behavior**:
- Steering files are now always generated by LLM (no regex fallback)
- Better quality output (no unfilled placeholders)
- Hallucination detection prevents incorrect information
- Atomic transactions ensure consistency

### For Developers

**Removed**:
- `TemplatePopulator` is no longer used in primary generation path
- `SteeringAssistant.generate_file()` is replaced by `SteeringFileGenerator`

**New APIs**:
```python
# Use case determination
from hiveforge.steering.input_resolver import InputResolver
resolver = InputResolver()
use_case, source_folder = resolver.resolve(...)

# Code analysis (structured output)
from hiveforge.steering.analyzers.code_analyzer import CodeAnalyzer
analyzer = CodeAnalyzer(project_root)
code_facts = analyzer.to_facts()  # Returns CodeAnalysisFacts

# Document parsing (bounded)
from hiveforge.steering.parsers.orchestrator import DocumentParser
parser = DocumentParser(source_folder)
source_docs = parser.parse_all()

# Delta analysis
from hiveforge.steering.delta_analyzer import DeltaAnalyzer
delta_analyzer = DeltaAnalyzer()
delta = delta_analyzer.analyze(source_docs, code_facts, existing_steering)

# Context assembly
from hiveforge.steering.context_assembler import ContextAssembler
assembler = ContextAssembler()
context = assembler.assemble(template_name, ...)

# Prompt building
from hiveforge.steering.prompt_builder import PromptBuilder
builder = PromptBuilder()
system_prompt, user_prompt = builder.build(template_name, template_content, context)

# File generation
from hiveforge.steering.steering_file_generator import SteeringFileGenerator
generator = SteeringFileGenerator(llm_provider)
result = await generator.generate_all_files(...)
```

## Performance Characteristics

### Token Usage

- **Per template**: ≤8,000 tokens context + ~3,000 tokens output = ~11,000 tokens
- **Total for 8 files**: ~88,000 tokens (~$0.13 with GPT-4 pricing)

### Execution Time

- **Code analysis**: ~2-5 seconds (depends on codebase size)
- **Document parsing**: ~0.1-1 second (depends on document count)
- **LLM calls**: ~30-60 seconds (8 sequential calls, ~4-8s each)
- **Total**: ~35-70 seconds for complete generation

### Scalability

- **Code analysis**: Automatic sampling for codebases >10k files
- **Document filtering**: Keyword-based relevance reduces token usage
- **Token budgets**: Hard limits prevent excessive API costs
- **Caching**: Response cache reduces redundant LLM calls (future enhancement)

## Known Limitations

### 1. Source Document Truncation

**Limitation**: When source documents exceed 4,000 tokens (even after keyword filtering), simple truncation is used with `[TRUNCATED]` markers.

**Impact**: Some document content may be omitted from LLM context.

**Mitigation**: 
- Keyword filtering prioritizes relevant content
- Most projects won't exceed 16,000 characters of relevant documentation per template
- Steering files are high-level summaries (don't need 100% completeness)

**Future Enhancement**: Implement chunking with overlap for large documents.

### 2. Sequential Generation

**Limitation**: Files are generated sequentially (not in parallel) to provide cross-file context.

**Impact**: Generation takes ~30-60 seconds for all 8 files.

**Mitigation**: Sequential generation is intentional (provides better quality via rolling summaries).

**Future Enhancement**: Parallel generation with dependency graph (e.g., generate `agents.md` and `workflows.md` in parallel after `architecture.md` completes).

### 3. LLM Dependency

**Limitation**: Requires LLM provider to be configured and available.

**Impact**: Cannot generate steering files without LLM access.

**Mitigation**: 
- Clear error messages when LLM unavailable
- MCP mode uses KIRO native LLM (no configuration needed)
- CLI mode requires explicit LLM configuration

**Future Enhancement**: Optional local LLM support (e.g., Ollama).
