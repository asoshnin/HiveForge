# Requirements Document

## Introduction

This feature refactors the HiveForge steering file generation pipeline from a regex-based `TemplatePopulator` fallback system to an LLM-primary synthesis engine. The current pipeline produces unusable output (copy-pasted paragraphs, unfilled placeholders, content bleeding across sections) because LLM is an optional afterthought reached only when explicitly configured. The fix is a fundamental inversion: every steering file is generated by an LLM call, with Python code responsible only for preparing structured context and writing validated output atomically to disk.

The refactor introduces five new components (`CodeAnalysisFacts`, `ContextAssembler`, `SteeringFileGenerator`, `DeltaAnalyzer`, `PromptBuilder`) while preserving the existing `LLMProvider` priority chain, `CodeAnalyzer` local analysis logic, template structure (8 files), `SteeringValidator`, `BackupManager`, and MCP tool interface.

## Glossary

- **CodeAnalysisFacts**: A JSON-serializable dataclass that replaces prose summaries as the output format of `CodeAnalyzer`. Contains structured fields: `primary_language`, `frameworks`, `dependencies`, `architecture_pattern`, `has_tests`, `test_framework`, `api_type`, `database`, `entry_points`, `naming_conventions`, `directory_structure`.
- **ContextAssembler**: A new component that enforces strict per-template token budgets (8,000 tokens total) by extracting only template-relevant content from source documents, code facts, existing steering files, and previously generated files.
- **DeltaAnalyzer**: An LLM-based component that computes three-way structural differences between design documents, codebase facts, and existing steering files to produce a `DeltaReport`.
- **DeltaReport**: A structured output from `DeltaAnalyzer` containing `doc_vs_code`, `steering_vs_code`, `steering_vs_docs`, and `missing_in_all` divergence lists.
- **GenerationContext**: A dataclass produced by `ContextAssembler` containing the assembled, token-budgeted inputs for a single template's LLM prompt.
- **GenerationResult**: The output of `SteeringFileGenerator.generate_all_files()`, indicating success/failure and the list of files written.
- **LLMProvider**: The existing component managing the priority chain: KIRO native (`ctx.sample()`) → Vertex AI → OpenAI.
- **PromptBuilder**: A new component that constructs one structured LLM prompt (system + user) per steering template from a `GenerationContext`.
- **Source Folder**: The explicitly designated folder containing user-provided design documents. Defaults to `.kiro/onboarding`. Nothing outside this folder is used as source material for document parsing.
- **SteeringFileGenerator**: A new component that orchestrates transactional generation of all 8 steering files: all succeed or none are written to disk.
- **SteeringValidator**: The existing post-generation validation component. Unchanged.
- **BackupManager**: The existing backup and rollback component. Unchanged.
- **Template**: One of the 8 steering file templates (e.g., `project-vision.md`, `tech-stack.md`, `architecture.md`, etc.).
- **Rolling Summary**: A compact, token-limited representation of a previously generated steering file used as cross-file context in subsequent prompts, as opposed to raw file text.

## Requirements

### Requirement 1: LLM as Primary Synthesis Engine

**User Story:** As a developer using HiveForge, I want every steering file to be generated by an LLM call so that the output is coherent, section-specific, and free of copy-pasted or placeholder content.

#### Acceptance Criteria

1. THE `SteeringFileGenerator` SHALL invoke `LLMProvider` for every steering template; no template SHALL be populated via regex substitution or keyword injection.
2. WHEN `LLMProvider` is unavailable (no provider configured and not in MCP mode), THE `SteeringFileGenerator` SHALL raise an explicit error and halt generation without writing any files.
3. IF `LLMProvider` returns an empty or malformed Markdown response, THEN THE `SteeringFileGenerator` SHALL retry the generation once using a simplified prompt before treating the attempt as failed.
4. THE `PromptBuilder` SHALL construct one structured prompt per template containing: template section schema, source document content, code facts, existing steering content, delta report, and user intent.
5. THE `PromptBuilder` SHALL include explicit instructions in every prompt: fill every section independently, write `N/A` for absent information, output only final Markdown with no preamble.

---

### Requirement 2: Structured Code Analysis Facts

**User Story:** As a developer, I want the code analyzer to output structured facts rather than prose summaries so that LLM prompts receive precise, non-repetitive context about the codebase.

#### Acceptance Criteria

1. THE `CodeAnalyzer` SHALL produce a `CodeAnalysisFacts` dataclass as its primary output, replacing the existing `to_summary()` prose method.
2. THE `CodeAnalysisFacts` dataclass SHALL be JSON-serializable and SHALL contain at minimum: `primary_language`, `frameworks`, `dependencies`, `architecture_pattern`, `has_tests`, `test_framework`, `api_type`, `database`, `entry_points`, `naming_conventions`, `directory_structure`.
3. THE `CodeAnalyzer` SHALL preserve all existing AST and regex parsing logic; only the output format changes from prose to structured facts.
4. WHEN a `hiveforge steering init` command performs a deep directory traversal, THE `CodeAnalyzer` SHALL display real-time progress indicators (e.g., `Scanning directory X of Y`) to the CLI output.
5. THE `CodeAnalysisFacts` SHALL serialize to a compact JSON representation with a maximum size of 2,000 tokens when injected into an LLM prompt.

---

### Requirement 3: Bounded Source Document Scope

**User Story:** As a developer, I want source documents to be read exclusively from the designated source folder so that test fixtures, generated files, and unrelated repository content cannot pollute the steering file context.

#### Acceptance Criteria

1. THE `DocumentParser` SHALL read source documents exclusively from the explicitly designated source folder (default: `.kiro/onboarding`).
2. THE `DocumentParser` SHALL NOT scan the project tree outside the designated source folder when assembling source document context.
3. WHEN a source folder path is provided via CLI argument or MCP tool parameter, THE `InputResolver` SHALL use that path exclusively for document parsing.
4. IF the designated source folder is empty or absent, THEN THE `InputResolver` SHALL proceed with code analysis only and set `source_docs` to an empty list in the `GenerationContext`.
5. THE `InputResolver` SHALL determine the applicable use case (`new_from_docs`, `reverse_engineer`, `drift_correction`, `update`) based on the presence or absence of source documents, codebase, and existing steering files.

---

### Requirement 4: Token-Budgeted Context Assembly

**User Story:** As a developer, I want the context fed to each LLM prompt to be strictly bounded so that the LLM receives focused, relevant information without context window bloat or "lost in the middle" degradation.

#### Acceptance Criteria

1. THE `ContextAssembler` SHALL enforce a maximum of 8,000 tokens of assembled context per template generation call.
2. THE `ContextAssembler` SHALL allocate token budgets per template as follows: source documents maximum 4,000 tokens, code facts maximum 2,000 tokens, existing steering file maximum 1,000 tokens, previously generated files maximum 1,000 tokens.
3. THE `ContextAssembler` SHALL extract only template-relevant paragraphs from source documents using keyword-based relevance filtering keyed to each template's section schema.
4. WHEN cross-file context from previously generated steering files is included, THE `ContextAssembler` SHALL use rolling summaries or extracted fields rather than raw file text.
5. IF the total assembled context for a template exceeds the 8,000 token limit after filtering, THEN THE `ContextAssembler` SHALL truncate lower-priority sections (previously generated files first, then existing steering, then code facts) to fit within the budget.
6. THE `ContextAssembler` SHALL produce a `GenerationContext` struct per template containing: `use_case`, `source_docs` (filtered), `code_facts` (filtered), `existing_steering` (truncated), `delta` (if applicable), `user_intent` (if provided).

---

### Requirement 5: Transactional Steering File Generation

**User Story:** As a developer, I want steering file generation to be atomic so that a failure mid-generation never leaves my workspace in a partially updated state.

#### Acceptance Criteria

1. THE `SteeringFileGenerator` SHALL generate all 8 steering files in memory before writing any file to disk.
2. WHEN all 8 in-memory drafts pass validation, THE `SteeringFileGenerator` SHALL write all files to `.kiro/steering/` in a single atomic operation.
3. IF any in-memory draft fails validation, THEN THE `SteeringFileGenerator` SHALL discard all drafts and return a `GenerationResult` with `success=False` without modifying the file system.
4. THE `SteeringFileGenerator` SHALL generate templates in a fixed sequential order so that each template can receive rolling summaries of previously generated templates as cross-file context.
5. THE `SteeringFileGenerator` SHALL return a `GenerationResult` containing: `success` flag, list of files written (empty on failure), and a list of validation errors encountered.

---

### Requirement 6: Deterministic Hallucination Detection

**User Story:** As a developer, I want the system to detect when the LLM has fabricated facts that contradict the analyzed codebase so that steering files never contain provably incorrect infrastructure information.

#### Acceptance Criteria

1. THE `SteeringFileGenerator` SHALL validate each generated draft against `CodeAnalysisFacts` using deterministic string-matching rules before the draft is accepted.
2. WHEN `CodeAnalysisFacts` specifies a database value and the generated `tech-stack.md` draft contains a different database name, THE `SteeringFileGenerator` SHALL treat this as a hallucination error.
3. WHEN `CodeAnalysisFacts` specifies a backend framework and the generated draft contradicts it, THE `SteeringFileGenerator` SHALL treat this as a hallucination error.
4. IF a hallucination error is detected, THEN THE `SteeringFileGenerator` SHALL immediately abort the entire transaction without triggering a retry loop.
5. IF the LLM returns an empty response or syntactically malformed Markdown (not a hallucination), THEN THE `SteeringFileGenerator` SHALL trigger `RetryWithSimplifiedPrompt` for that template before aborting.
6. THE `SteeringFileGenerator` SHALL NOT attempt to auto-correct hallucinated content; the system SHALL fail loudly with a descriptive error message identifying the conflicting field.

---

### Requirement 7: Delta-Aware Generation for Drift Correction

**User Story:** As a developer, I want the system to detect divergences between my design documents, codebase, and existing steering files so that updated steering files accurately reconcile all three sources of truth.

#### Acceptance Criteria

1. THE `DeltaAnalyzer` SHALL compare design document content, `CodeAnalysisFacts`, and existing steering file content to produce a `DeltaReport`.
2. THE `DeltaReport` SHALL contain: `doc_vs_code` (divergences between design docs and codebase), `steering_vs_code` (drifts between steering files and codebase), `steering_vs_docs` (conflicts between steering files and design docs), `missing_in_all` (gaps absent from all three sources).
3. WHEN the `use_case` is `drift_correction` or `update`, THE `PromptBuilder` SHALL include the `DeltaReport` in the LLM prompt for each template.
4. THE `DeltaAnalyzer` SHALL detect structural drift only (e.g., technology mismatches, dependency changes) and SHALL NOT attempt to detect behavioral or architectural boundary violations.
5. WHEN design documents and codebase diverge on a factual field, THE `PromptBuilder` SHALL instruct the LLM to prefer design documents as the source of truth unless `user_intent` specifies otherwise.

---

### Requirement 8: LLM Provider Availability Enforcement

**User Story:** As a developer, I want the system to fail loudly when no LLM is available rather than silently producing garbage output via regex fallback so that I always know whether my steering files are trustworthy.

#### Acceptance Criteria

1. WHEN running in MCP mode, THE `LLMProvider` SHALL use `ctx.sample()` as the default provider without requiring additional configuration.
2. WHEN running in CLI mode without a configured LLM provider, THE `LLMProvider` SHALL raise an explicit `LLMUnavailableError` with a message describing how to configure a provider.
3. THE `SteeringFileGenerator` SHALL NOT fall back to `TemplatePopulator` or any regex-based generation path under any circumstances.
4. IF `LLMProvider` raises `LLMUnavailableError`, THEN THE `SteeringFileGenerator` SHALL propagate the error to the caller without writing any files.
5. THE `LLMProvider` SHALL implement retry logic with exponential backoff for transient API errors before raising a terminal error.

---

### Requirement 9: Use Case Support

**User Story:** As a developer, I want the pipeline to handle all five generation scenarios (new project, reverse engineering, drift correction, error recovery, pivot) so that HiveForge is useful regardless of the project's current state.

#### Acceptance Criteria

1. WHEN source documents exist and no codebase is present, THE `SteeringFileGenerator` SHALL generate steering files from source documents only, writing `N/A` for sections that cannot be inferred from documents alone.
2. WHEN a codebase exists and no source documents are present, THE `SteeringFileGenerator` SHALL generate steering files from `CodeAnalysisFacts` only, writing `N/A` for sections that cannot be inferred from code structure alone (e.g., business goals, success metrics).
3. WHEN both source documents and a codebase exist alongside existing steering files, THE `SteeringFileGenerator` SHALL invoke `DeltaAnalyzer` and include the `DeltaReport` in all template prompts.
4. WHEN existing steering files are broken or incomplete, THE `SteeringFileGenerator` SHALL treat them as partial existing context and regenerate all 8 files from available inputs.
5. WHEN a user provides a new intent document in the source folder, THE `InputResolver` SHALL set `user_intent` in the `GenerationContext` and THE `PromptBuilder` SHALL include it explicitly in all template prompts.

---

### Requirement 10: Silence Over Hallucination (Output Quality)

**User Story:** As a developer, I want steering files to contain explicit `N/A` markers for unknown information rather than fabricated or repeated content so that I can trust what is written and know what is missing.

#### Acceptance Criteria

1. THE `PromptBuilder` SHALL instruct the LLM to write `N/A` for any section where the provided context contains no relevant information.
2. THE `PromptBuilder` SHALL instruct the LLM to write `[NOT FOUND]` for any field where information was expected but absent from all provided sources.
3. THE `PromptBuilder` SHALL instruct the LLM that each section must be filled independently and that content SHALL NOT be repeated across sections.
4. THE `PromptBuilder` SHALL instruct the LLM to output only the final Markdown document with no preamble, explanation, or meta-commentary.
5. WHEN a generated draft contains the same paragraph verbatim in more than one section, THE `SteeringFileGenerator` SHALL treat this as a validation error and reject the draft.
