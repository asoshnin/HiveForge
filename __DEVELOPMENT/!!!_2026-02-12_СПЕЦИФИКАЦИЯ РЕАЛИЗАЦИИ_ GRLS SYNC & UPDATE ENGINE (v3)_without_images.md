# **1\. АРХИТЕКТУРА И ТЕХНОЛОГИЧЕСКИЙ СТЕК**

Система использует **гибридную архитектуру сбора данных** с автоматическим управлением сессиями и восстановлением после сбоев.

## **1.1. Концепция Гибридного Движка (Hybrid Engine)**

Процесс сбора данных выполняется в три последовательные фазы с автоматическим управлением жизненным циклом:

1. **Фаза 1: Браузерный контроллер (Playwright).**  
     
   - **Задача:** Эмуляция действий пользователя, генерация валидных кук (ASP.NET\_SessionId), раскрытие скрытых ссылок через JS-события.  
   - **Результат:** Экспорт «Cookie Jar» (контейнера сессии) и прямых ссылок на файлы.  
   - **Автоматизация:** Автоматическое обнаружение истечения сессии и перезапуск при необходимости.

   

2. **Фаза 2: Сетевой экстрактор (HTTPX \+ curl\_cffi).**  
     
   - **Задача:** Асинхронное скачивание тысяч PDF-файлов и HTML-страниц с использованием сессии, полученной на Фазе 1\.  
   - **Механизм "Session Bridge":** Передача `context.cookies()` от браузера в HTTP-клиент позволяет избежать блокировок WAF и ускоряет сбор данных в 10–20 раз по сравнению с чистым Selenium/Playwright.  
   - **Автоматизация:** Автоматическое обнаружение сбоев сессии и возврат к Фазе 1 без ручного вмешательства.

   

3. **Фаза 3: Обработка и валидация (Automated Pipeline).**  
     
   - **Задача:** Автоматическая обработка документов, валидация данных, разрешение конфликтов.  
   - **Автоматизация:** Полностью автоматический процесс с минимальными точками ручного вмешательства.

## **1.2. Технологический стек**

### **Ядро системы (Core)**

* **Язык:** Python 3.10+ (строгая типизация с использованием `typing` и `dataclasses`).  
* **Валидация данных:** Pydantic v2.x. Обеспечивает жесткое соблюдение схемы данных на этапе парсинга, отбрасывая некорректные записи до записи в БД.  
* **Управление сессиями:** Новый модуль `SessionManager` для автоматического управления жизненным циклом сессий.

### **Модуль скрапинга (Scraping Layer)**

* **Browser Automation:** Playwright (Python). Используется для рендеринга JS и обхода защиты `__EVENTVALIDATION` на этапе поиска обновлений.  
* **Network Client:** `httpx` (async) в связке с `curl_cffi`. Библиотека `curl_cffi` необходима для маскировки TLS-отпечатков (TLS Fingerprint Evasion).  
* **Session Management:** Новый модуль `SessionManager` автоматически управляет TTL сессий, их обновлением и восстановлением.

### **Обработка документов (Document Processing)**

* **PDF Extraction:** Библиотека `pdfplumber` для извлечения табличных данных и координат текста.  
* **OCR & Semantic Cleanup:** Google Gemini 3 Flash с оптимизацией затрат:  
  - **Кэширование:** Извлеченный текст кэшируется по MD5 хешу PDF для избежания повторных запросов.  
  - **Batch Processing:** Группировка небольших документов в батчи для снижения количества API-вызовов.  
  - **Fallback Strategy:** Использование бесплатного Tesseract OCR для простых документов перед обращением к Gemini.  
* **Document Classification:** Автоматический классификатор типов документов с использованием эвристик вместо LLM для снижения затрат.

### **Хранение данных (Storage)**

* **Metadata DB:** PostgreSQL 14+ с поддержкой JSONB.  
* **Document Storage:** JSONL (JSON Lines) для совместимости с легаси-системой.  
* **Cache Layer:** Redis для кэширования сессий, извлеченного текста и метаданных.

### **Мониторинг и алертинг (NEW)**

* **Логирование:** Structured logging через `structlog` с интеграцией в ELK Stack или Loki.  
* **Метрики:** Prometheus для сбора метрик производительности и затрат.  
* **Алертинг:** AlertManager для отправки уведомлений через Email, Slack, Telegram.  
* **Трассировка:** OpenTelemetry для распределенной трассировки запросов.

# **2\. СТРАТЕГИЯ ПЕРВИЧНОЙ СВЕРКИ (Baseline Reconciliation)**

Перед запуском ежедневного парсера необходимо устранить разрыв между статическим дампом GEOTAR (29 000+ записей) и актуальным реестром ГРЛС. ГРЛС является единственным источником истины («Golden Truth»).

## **2.1. Нормализация первичных ключей**

Для сверки используется алгоритм нормализации `normalize_reg_nr`:

1. **Очистка (Sanitization):** Удаление пробелов в начале и конце строки. Приведение к верхнему регистру.  
2. **Замена разделителей:** Замена всех пробелов на дефисы.  
3. **Устранение коллизий:** Нормализация похожих символов кириллицы/латиницы (A/А, B/В, C/С).  
4. **Удаление суффиксов:** Обрезка «хвостов», добавленных при переоформлении удостоверений. Регулярное выражение: `^(.*?)(?:-\d{6})?$` отсекает дату после дефиса, оставляя только базовый номер.

**Улучшение:** Добавлена автоматическая валидация нормализованных номеров через регулярные выражения для обнаружения некорректных форматов.

## **2.2. Конвейер нечеткого поиска (Fuzzy Discovery Pipeline)**

Система использует трехуровневый каскад поиска соответствий:

* **Tier 1 (Точное совпадение):** Поиск по нормализованному `RegNr`. Покрывает \~85% записей.  
* **Tier 2 (Цифровой след):** Сравнение только цифровой части номера (удаление всех буквенных префиксов). Позволяет связать записи вида `ЛС-001234` и `П N001234`.  
* **Tier 3 (Семантическое совпадение):** Если `RegNr` не найден, выполняется поиск по совокупности полей: МНН \+ Производитель \+ Торговое наименование. Используется метрика Левенштейна (Token Sort Ratio) с порогом сходства \> 90%.

**Улучшение:** Добавлена автоматическая оценка качества совпадений с пороговыми значениями для автоматического принятия решений без ручного вмешательства.

## **2.3. Разрешение конфликтов и "Золотая запись"**

При обнаружении расхождений между локальной базой (GEOTAR) и данными реестра (ГРЛС) применяются следующие правила приоритета:

1. **Статус активности:** Если GEOTAR указывает статус "Действует", а ГРЛС не находит препарат или помечает его как "Отменен/Истек", локальной записи присваивается статус `ARCHIVED`.  
2. **Принудительное обновление (Freshness Trigger):** Если статус совпадает, но количество документов в ГРЛС превышает количество документов в GEOTAR, запись помечается флагом `FORCE_UPDATE` для загрузки недостающих файлов.  
3. **Доверие метаданным:** Даты регистрации и окончания действия перезаписываются значениями из ГРЛС.

**Улучшение:** Добавлена автоматическая логика разрешения конфликтов с минимальным количеством случаев, требующих ручного вмешательства.

Результатом работы данного этапа является файл `baseline_map.json`, связывающий `geotar_id` с `grls_routing_guid`.

# **3\. СПЕЦИФИКАЦИЯ ГИБРИДНОГО ПАРСЕРА (The Hybrid Scraper)**

Ежедневное обновление данных выполняется скриптом `daily_updater.py`. Процесс разделен на три изолированные фазы с автоматическим управлением жизненным циклом.

## **3.1. Фаза 1: Браузерный контроллер (Stateful Search & Exposure)**

**Инструмент:** Playwright (Python). **Режим:** Headless Chromium.  
**Конфигурация:** Обязательная установка фиксированного `User-Agent`, который будет идентичен используемому в `curl_cffi` на Фазе 2\.

**⚠️ ВАЖНО:** Playwright используется **НЕ для скачивания PDF**, а исключительно для:

1. Получения валидной сессии (`ASP.NET_SessionId`) через обход защиты ViewState  
2. Раскрытия скрытых ссылок на PDF через эмуляцию JS-событий (клик по `#instructionsCaller`)

**Альтернативный подход:** Перед реализацией необходимо проверить возможность получения ссылок на PDF без использования браузера (например, через анализ сетевых запросов или прямые API-вызовы). Если ссылки доступны напрямую, можно использовать только `httpx` с предварительно полученной сессией через один раз запущенный Playwright или через ручное получение cookies.

### **Шаг 1: Инициализация и обход фильтров**

1. Скрипт открывает страницу поиска `grls.rosminzdrav.ru/grls.aspx`.  
2. **Эмуляция PostBack:** Для фильтрации по дате скрипт перехватывает и сохраняет токены `__VIEWSTATE` и `__EVENTVALIDATION`.  
3. Заполняются поля фильтра "Дата изменения" (от `Last_Run_Date` до `Current_Date`).  
4. Скрипт активирует поиск, ожидая перезагрузки DOM-дерева.

**Улучшение:** Добавлена автоматическая валидация наличия токенов ViewState перед отправкой POST-запроса.

### **Шаг 2: Извлечение идентификаторов (Routing GUIDs)**

Из таблицы результатов поиска извлекаются ссылки на детальные карточки препаратов.

* **Паттерн:** `Grls_View_v2.aspx?routingGuid={UUID}&t=`  
* **Действие (Batching):** Формируется пакет (batch) из 50–100 `routingGuid`. Обработка ведется потоково: как только пакет собран, он немедленно передается в Фазу 2, чтобы успеть скачать файлы до истечения времени жизни сессии (Session Time-To-Live \~20 мин).

**Улучшение:** Добавлена автоматическая обработка пагинации для извлечения всех результатов поиска.

### **Шаг 3: Раскрытие скрытых ссылок (The "Click" Action)**

Для каждого найденного `routingGuid` Playwright выполняет навигацию на страницу препарата.

* **Проблема:** Ссылки на PDF-инструкции отсутствуют в исходном HTML. Они подгружаются динамически.  
* **Решение:** Скрипт находит кнопку с ID `#instructionsCaller` и эмулирует физический клик.  
* **Ожидание:** `page.wait_for_selector(".tblInstr", state="attached", timeout=10000)`.  
* **Экспорт:** Из появившейся таблицы извлекаются прямые ссылки на PDF (обычно `/InstrImg/.../*.pdf`).

**Улучшение:** Добавлена автоматическая обработка случаев, когда кнопка `#instructionsCaller` отсутствует или таблица не загружается.

### **Результат Фазы 1:**

Формируется манифест задач `job_manifest.json` и файл сессии `cookies.json` (Session Bridge), содержащий валидный `ASP.NET_SessionId`. Сессия сохраняется в Redis с TTL 20 минут.

## **3.2. Фаза 2: Сетевой экстрактор (Stateless Extraction)**

**Инструмент:** `httpx` (Async) \+ `curl_cffi`. **Задача:** Высокоскоростная асинхронная загрузка контента без накладных расходов на рендеринг браузера. **Все скачивание PDF выполняется через `httpx`**, а не через Playwright. Playwright используется только на Фазе 1 для получения сессии и раскрытия ссылок.

### **Механизм Session Bridge**

Клиент `httpx` инициализируется с использованием кук, экспортированных на Фазе 1 или полученных из кэша сессий. Это позволяет делать прямые GET-запросы к страницам и файлам.

**Улучшение:** Добавлен автоматический менеджер сессий, который проверяет валидность сессии перед использованием и автоматически запрашивает новую при необходимости.

### **Алгоритм загрузки:**

1. **Загрузка HTML метаданных:** Асинхронный запрос GET к странице препарата (по `routingGuid`). HTML сохраняется в `raw_html/` для последующего парсинга полей.  
2. **Загрузка бинарных файлов (PDF):**  
   * Используются ссылки из `job_manifest.json`.  
   * **Маскировка TLS:** Используется `curl_cffi` для имитации TLS-отпечатка браузера Chrome (JA3 Fingerprint).  
   * **Валидация:** Проверка заголовка `Content-Type` (должен быть `application/pdf`). Если получен `text/html`, это признак "слетевшей" сессии — автоматически запускается перезапуск Фазы 1\.

**Улучшение:** Добавлена автоматическая проверка целостности PDF-файлов (валидация заголовков) перед сохранением.

## **3.3. Фаза 3: Автоматическая обработка и валидация (NEW)**

**Задача:** Автоматическая обработка загруженных данных с минимальным человеческим вмешательством.

### **Шаг 1: Автоматическая валидация данных**

Каждая запись проходит валидацию через Pydantic-модель перед сохранением:

* **Critical Fail:** Если отсутствует `mnn` или `registrationnumber`, запись отбрасывается и логируется для последующего анализа.  
* **Soft Fail:** Если отсутствует `AtcCode` или `PharmacotherapeuticGroup`, запись сохраняется, но помечается флагом `DATA_INCOMPLETE`.

### **Шаг 2: Автоматическое разрешение конфликтов**

Система автоматически разрешает конфликты по следующим правилам:

1. **Проверка флага `manual_override`:** Если установлен, запись пропускается автоматически.  
2. **Сравнение хешей:** Если `hash_sum` нового PDF совпадает со старым, обновление не требуется.  
3. **Автоматическое обновление:** Если данные изменились и нет блокировки, выполняется автоматическое обновление.

### **Шаг 3: Автоматическое логирование и мониторинг**

Все действия автоматически логируются с метриками:

- Количество обработанных записей  
- Количество обновленных записей  
- Количество пропущенных записей (с причинами)  
- Затраты на обработку (токены Gemini, время выполнения)

## **3.4. Защита и отказоустойчивость**

* **Rate Limiting:** Жесткое ограничение — не более 1 запроса в 2 секунды к домену `grls.rosminzdrav.ru`.  
* **Retry Policy:** Экспоненциальная задержка (Exponential Backoff) при ошибках 500/503. Максимум 3 попытки с автоматическим увеличением задержки.  
* **Binary Garbage Check:** Перед сохранением PDF проверяется на наличие бинарного мусора в заголовках.  
* **Автоматическое восстановление:** При обнаружении сбоев сессии система автоматически перезапускает Фазу 1 без ручного вмешательства.

**Улучшение:** Добавлена автоматическая обработка сетевых ошибок с экспоненциальным backoff и автоматическим восстановлением.

# **3.5. АЛГОРИТМ ЕЖЕДНЕВНОГО ОБНОВЛЕНИЯ ПРЕПАРАТОВ (Daily Update Cycle)**

Ежедневный цикл обновления выполняется скриптом `daily_updater.py` и включает явную логику обнаружения новых препаратов и обновления существующих.

## **3.5.1. Обнаружение изменений и новых препаратов**

### **Шаг 1: Получение списка измененных препаратов**

1. **Фильтрация по дате изменения:**  
     
   - Запрос к ГРЛС с фильтром "Дата изменения" от `Last_Run_Date` до `Current_Date`  
   - Извлечение всех `routingGuid` из результатов поиска  
   - Формирование списка `changed_routing_guids[]`

   

2. **Обработка пагинации:**  
     
   - Автоматический обход всех страниц результатов поиска  
   - Сбор полного списка измененных препаратов за период

### **Шаг 2: Классификация записей**

Для каждого `routingGuid` из `changed_routing_guids[]`:

1. **Проверка существования в базе:**

```py
existing_record = db.query_by_routing_guid(routing_guid)
```

2. **Классификация:**  
     
   - **Новый препарат:** `existing_record is None` → добавить в очередь `new_drugs[]`  
   - **Обновление существующего:** `existing_record exists` → добавить в очередь `updates[]`

### **Шаг 3: Обработка новых препаратов**

Для каждого препарата из `new_drugs[]`:

1. Загрузка HTML метаданных (Фаза 2\)  
2. Извлечение всех ссылок на PDF инструкции  
3. Загрузка PDF файлов  
4. Обработка через OCR (если требуется)  
5. Валидация через Pydantic  
6. **Создание новой записи** в БД с полем `first_seen_date = Current_Date`  
7. Логирование: `NEW_DRUG_ADDED` с метаданными

### **Шаг 4: Обработка обновлений существующих препаратов**

Для каждого препарата из `updates[]`:

1. **Проверка флага `manual_override`:**  
     
   - Если `manual_override = True` → пропустить обновление, обновить только `last_sync_attempt`  
   - Логирование: `UPDATE_SKIPPED_MANUAL_LOCK`

   

2. **Сравнение хешей PDF:**  
     
   - Загрузка текущего PDF из ГРЛС  
   - Вычисление `new_hash_sum = MD5(current_pdf)`  
   - Сравнение с `existing_record.hash_sum`

   

3. **Принятие решения:**  
     
   - **Если `new_hash_sum == existing_record.hash_sum`:**  
       
     - Обновить только `last_sync_attempt` и `last_checked_date`  
     - Логирование: `NO_CHANGES_DETECTED`

     

   - **Если `new_hash_sum != existing_record.hash_sum`:**  
       
     - Загрузить новый PDF  
     - Обработать через OCR (если требуется)  
     - Применить алгоритм слияния изменений (Anchor-Replacement)  
     - Создать новую версию документа (`ver_X+1.json`)  
     - Обновить запись в БД: `hash_sum`, `last_updated_at`, `raw_json`  
     - Логирование: `DRUG_UPDATED` с указанием измененных полей

### **Шаг 5: Обработка архивных препаратов**

После обработки всех изменений:

1. **Проверка препаратов, отсутствующих в ГРЛС:**  
     
   - Для всех записей в БД с `status = ACTIVE` и `last_checked_date < Current_Date - 30 days`  
   - Выполнить поиск в ГРЛС по `routingGuid`

   

2. **Если препарат не найден в ГРЛС:**  
     
   - Обновить статус: `status = ARCHIVED`  
   - Установить `archived_date = Current_Date`  
   - Логирование: `DRUG_ARCHIVED`

## **3.5.2. История изменений препарата**

# **5\. ЛОГИКА: ДВИЖОК РАСЧЕТА СТАТУСОВ (Status Calculation Engine)**

В реестре ГРЛС отсутствует явное поле "Статус" (Active/Expired). Статус препарата является **расчетным атрибутом**, вычисляемым на основе комбинации дат регистрации, окончания действия и текстовых меток о бессрочном обращении.

## **5.1. Входные переменные**

Для расчета используются следующие поля, извлеченные на этапе парсинга:

| Переменная | Источник (DOM ID) | Описание | Обязательность |
| :---- | :---- | :---- | :---- |
| `reg_date_fin` | `#ctl00_plate_RegDateFin` | Дата окончания действия регистрационного удостоверения (РУ). | Опциональное |
| `circulation_period` | `#ctl00_plate_txtCirculationPeriod` | Текстовое поле. Может содержать дату или маркер «Бессрочный». | Опциональное |
| `reg_date_ch` | `#ctl00_plate_DChange` | Дата последнего переоформления РУ. | Опциональное |
| `cancellation_date` | (Отсутствует в карточке) | Данные об отмене регистрации публикуются в отдельных приказах. | Не используется |

**Улучшение:** Добавлена колонка "Обязательность" для ясности требований к данным.

## **5.2. Алгоритм вычисления (The Formula)**

Статус определяется каскадной проверкой условий. Как только одно из условий выполняется, алгоритм возвращает результат и останавливается.

**Шаг 1: Проверка на бессрочность**  
Если поле `circulation_period` содержит подстроку "Бессрочный" (без учета регистра), статус \= `ACTIVE`.

**Шаг 2: Расчет эффективной даты окончания (Effective Expiry)**  
Если явной метки "Бессрочный" нет, вычисляется дата истечения срока:

* **Формула:** `EffectiveExpiry = Max(reg_date_fin, reg_date_ch + 5 years)`  
* Если `reg_date_ch` присутствует, к ней добавляется 5 лет (стандартный срок действия РУ в РФ). Берется более поздняя из двух дат.

**Шаг 3: Финальная сверка с календарем**

* Если `EffectiveExpiry` \>= `CurrentDate` (сегодня), статус \= `ACTIVE`.  
* В противном случае, статус \= `EXPIRED`.

**Улучшение:** Алгоритм остался без изменений, но добавлена более детальная документация.

## **5.3. Обработка пограничных случаев (Edge Cases)**

1. **Пустые даты:** Если `reg_date_fin` и `reg_date_ch` отсутствуют или равны `null` (и нет метки "Бессрочный"), статус помечается как `MANUAL_REVIEW`.  
2. **Артефакты ввода:** Поля дат часто содержат символы `~` или опечатки. Перед расчетом применяется строгий парсер формата даты. Если парсинг невозможен, срабатывает правило `MANUAL_REVIEW`.  
3. **Триггер безопасности (Risk Check):** Если расчетный статус `ACTIVE`, но дата последнего обновления записи (`LastUpdated`) старше 6 месяцев, выставляется флаг `VERIFY_CANCELLATION` для автоматической сверки.

**Улучшение:** Добавлена автоматическая обработка флага `VERIFY_CANCELLATION` без ручного вмешательства.

## **5.4. Итоговые статусы системы**

Система оперирует только тремя статусами:

* `ACTIVE` — Препарат действующий, инструкции подлежат обновлению.  
* `EXPIRED` — Срок регистрации истек. Обновления не требуются.  
* `MANUAL_REVIEW` — Недостаточно данных для автоматического решения. **Улучшение:** Записи с этим статусом автоматически помечаются для последующего анализа, но не блокируют работу системы.

# **6\. ПРОДВИНУТАЯ ОБРАБОТКА ДОКУМЕНТОВ (Advanced Document Processing)**

Система должна обрабатывать не только полные тексты инструкций, но и файлы "Изменений" (Diffs), которые публикуются в реестре ГРЛС как отдельные документы.

## **6.1. Классификатор входящих документов (Ingestion Classifier)**

Обработка документов делегируется существующему корпоративному **OCR-пайплайну**.

**Логика маршрутизации:** Система использует встроенный детектор слоя (Image vs Native Text):

1. **Native Text PDF:** Извлекается через `pdfplumber` / `PyMuPDF`.  
2. **Raster/Image PDF:** Автоматически отправляется в **Google Gemini 3 Flash** для распознавания.

**Специфическая классификация ГРЛС:** Поверх базового OCR применяется логический классификатор типа документа:

* **Full Instruction:** Заголовок содержит "Инструкция по медицинскому применению".  
* **Diff Type A (Structured):** Наличие колонок "Старая редакция" / "Новая редакция".  
* **Diff Type B (Unstructured):** Текстовые приказы об изменениях.

**Улучшение:** Добавлена автоматическая классификация документов с использованием эвристик вместо LLM для снижения затрат.

## **6.2. Стратегии извлечения (Extraction Strategies)**

### **Стратегия A: Детерминированный экстрактор колонок (Column Extractor)**

Применяется для документов **Type A** (таблицы сравнения).

* **Инструмент:** `pdfplumber`.  
* **Алгоритм:**  
  1. Определение координат (Bounding Box) таблицы изменений.  
  2. Фильтрация вертикальных линий для разделения страницы на две зоны: Left (Старая) и Right (Новая).  
  3. Игнорирование содержимого левой колонки.  
  4. Построчное извлечение текста из правой колонки.  
  5. **Склейка:** Объединение строк, разорванных границами ячеек, в единые параграфы.

### **Стратегия B: Семантический экстрактор (Semantic Extraction)**

Применяется для документов **Type B** (приказы, сканы, сложная верстка).

* **Инструмент:** Google Gemini 3 Flash (Vision API).  
* **Конфигурация:** Temperature \= 0.1 (минимальная галлюцинация).  
* **System Prompt:** "Ты — оператор ввода медицинских данных. Твоя задача — преобразовать изображение документа в структурированный JSON. Извлеки только текст изменений, игнорируя юридические преамбулы. Сохраняй числовые значения (дозировки) с абсолютной точностью."

**Улучшение:** Добавлена стратегия кэширования результатов OCR по MD5 хешу документа для избежания повторных запросов.

## **6.3. Алгоритм слияния изменений (Context-Aware Merging)**

Используется алгоритм **"Якорь-Замена" (Anchor-Replacement):**

1. **Генерация якоря:** Из колонки "Старая редакция" (или контекста изменения) извлекается уникальная фраза (anchor) длиной 50–100 символов.  
2. **Нечеткий поиск (Fuzzy Search):** Выполняется поиск якоря в текущем полном тексте инструкции. Используется метрика Левенштейна (порог сходства \> 95%).  
   * *Critical Check:* Если якорь найден более одного раза, автоматическое слияние блокируется, выставляется флаг `MANUAL_MERGE_REQUIRED`.  
3. **Инкрементальная версия:**  
   * Исходный текст не перезаписывается.  
   * Создается новая ревизия документа: `ver_X+1.json`.  
   * В метаданные новой версии записывается `parent_diff_id`.

**Улучшение:** Добавлена автоматическая обработка случаев с множественными совпадениями якорей с использованием контекста для выбора правильного совпадения.

## **6.4. Очистка и нормализация (Sanitization)**

После экстракции текст проходит финальную чистку:

1. **Де-гифинация:** Склейка слов, разорванных переносом строки.  
2. **Восстановление единиц измерения:** Нормализация написания (мкг, мг, мл).  
3. **Удаление артефактов:** Очистка от служебных символов PDF.

# **7\. ИНФРАСТРУКТУРА И ЗАЩИТНЫЕ МЕХАНИЗМЫ (Infrastructure & Defense)**

## **7.1. Маскировка TLS-отпечатков (TLS Fingerprint Evasion)**

**Требование:** Весь сетевой трафик (Фаза 2\) должен проходить через библиотеку `curl_cffi`.

* **Конфигурация:** `impersonate="chrome110"`.  
* **Sync Check:** Строка User-Agent, генерируемая этой библиотекой, должна быть жестко прописана в настройках Playwright (Фаза 1).

## **7.2. Управление нагрузкой (Rate Limiting)**

* **Global Rate Limit:** Не более 30 запросов в минуту (1 запрос каждые 2 секунды) к одному домену.  
* **Реализация:** Использование примитива синхронизации `asyncio.Semaphore` или `Token Bucket` алгоритма.  
* **Concurrency:** На Фазе 2 допускается параллелизм до 5 потоков, но с соблюдением глобального лимита интервалов.

## **7.3. Проксирование и ротация IP**

* **Тип прокси:** Residential Proxies (Резидентные прокси). IP-адреса должны принадлежать домашним интернет-провайдерам РФ.  
* **Ротация и Сессия:** Смена IP-адреса выполняется только при получении 403/429.  
  * **ВАЖНО:** Так как `ASP.NET_SessionId` привязан к IP, смена прокси делает текущую сессию невалидной.  
  * **Action:** При ротации IP скрипт автоматически инвалидирует текущую сессию и перезапускает Фазу 1 через новый IP.

**Улучшение:** Добавлена автоматическая ротация прокси при обнаружении блокировок без ручного вмешательства.

## **7.4. Валидация "Тихих ошибок" (Silent Failures)**

Платформа ASP.NET часто возвращает HTTP-код `200 OK` даже при возникновении внутренней ошибки.

**Алгоритм валидации ответа:** Перед парсингом HTML каждый ответ проверяется на наличие стоп-фраз:

1. `"Invalid postback or callback argument"` — рассинхронизация сессии ViewState. Требуется перезапуск Фазы 1\.  
2. `"System.Web.HttpException"` — внутренняя ошибка сервера.  
3. `"Bot detected"` / `"Access denied"` — блокировка WAF.

Если в ответе найдена стоп-фраза, выбрасывается исключение `ContentValidationError`, которое активирует автоматическую политику повторных попыток.

## **7.5. Политика повторов (Retry Policy)**

Сетевые ошибки и таймауты обрабатываются по стратегии **Exponential Backoff**:

* **Попытка 1:** Задержка 2 сек.  
* **Попытка 2:** Задержка 4 сек.  
* **Попытка 3:** Задержка 8 сек.  
* **Попытка 4:** Critical Error. Задача помечается как `FAILED`, инцидент логируется и отправляется алерт.

## **7.6. Мониторинг целостности верстки (Canary Checks)**

Если парсер не находит критические селекторы (`#ctl00_plate_RegNr`, `#instructionsCaller`) в 5 документах подряд:

1. Работа скрипта аварийно останавливается.  
2. Отправляется уведомление `LAYOUT_CHANGED_ALERT` администратору.  
3. БД защищается от записи "пустых" значений.

**Улучшение:** Добавлена автоматическая отправка алертов через несколько каналов (Email, Slack, Telegram) для обеспечения надежности уведомлений.

2. **Обертка для Gemini API:**

```py
def gemini_ocr_with_tracking(pdf_path: str, prompt: str):
    trace = langfuse.trace(
        name="gemini_ocr",
        metadata={"pdf_path": pdf_path, "pdf_hash": md5_hash(pdf_path)}
    )
    
    generation = trace.generation(
        name="gemini_flash_vision",
        model="gemini-1.5-flash",
        model_parameters={"temperature": 0.1}
    )
    
    # Вызов Gemini API

        "input": result.input_tokens,
        "output": result.output_tokens,
        "total": result.total_tokens
    })
    
    trace.end()
    return result
```

## **1\. Problem Statement (Контекст)**

Необходимо автоматизировать процесс актуализации базы данных медицинских инструкций, используя в качестве источника государственный реестр (GRLS). Прямая интеграция отсутствует. Источник защищен от скрапинга (ASP.NET ViewState, динамический JS, WAF). Ручное обновление экономически нецелесообразно.

**Ключевой вызов:** Создать надежный конвейер (pipeline), который автономно собирает данные, но при этом умеет "останавливаться" при превышении бюджета или технических сбоях источника, не затирая ручные правки контент-менеджеров.

## **2\. Goals & Success Metrics**

### **2.1. North Star Metric (Экономическая эффективность)**

* **Cost Efficiency Ratio:** `(Стоимость 1 обновления через API) / (Стоимость 1 часа работы оператора * Среднее время ручного обновления) < 0.1`  
* **Цель:** Автоматическое обновление должно быть минимум в 10 раз дешевле ручного труда.

### **2.2. Engineering Goals**

1. **Zero Overwrite:** Ни одна запись, помеченная как "Проверено вручную", не должна быть перезаписана роботом.  
2. **Budget Safety:** Система должна автоматически приостановить работу при достижении лимита расходов (Cost Cap) до вмешательства администратора.  
3. **Autonomous Operation:** Система должна работать автономно с минимальным человеческим вмешательством (цель: \< 1% записей требуют ручного вмешательства).

## **3\. User Personas & Roles**

1. **System Engine (Robot):** Выполняет ETL-процесс. Приоритет прав — низкий (Low).  
2. **Content Manager (Human):** Вносит точечные правки в инструкции. Приоритет прав — высокий (High/Master).  
3. **DevOps / Admin:** Получает алерты, управляет конфигурацией бюджета и перезапуском пайплайна.

## **4\. Technical Architecture (Hybrid Engine)**

Система реализует трехступенчатый пайплайн с автоматическим управлением жизненным циклом.

### **4.1. Component Diagram (Logic)**

```
graph TD
    A[Scheduler / Trigger] --> B{Cost Guard Check}
    B -- Budget Exceeded --> C[Alert: Email & Pause]
    B -- Budget OK --> D[Session Manager]
    D --> E{Session Valid?}
    E -- No --> F[Phase 1: Playwright]
    E -- Yes --> G[Phase 2: HTTPX Client]
    F --> G
    G -- Raw HTML/PDF --> H[Phase 3: Parsing & OCR]
    H --> I{Conflict Resolver}
    I -- Manual Flag = True --> J[Skip Update]
    I -- Manual Flag = False --> K[Update DB Superset]
    K --> L[Log Cost Usage]
    L --> M[Update Metrics]
```

### **4.2. Detailed Requirements by Module**

#### ***Модуль 1: Cost Guard (Фин-контроль)***

* **Функция:** Перед запуском каждой пачки (batch) обновлений проверяет накопленные расходы за текущий месяц.  
* **Логика:**  
* `Current_Cost` \= (Кол-во токенов Gemini \* Price) \+ (Infrastructure Costs)  
* Если `Current_Cost` \>= `MONTHLY_BUDGET_THRESHOLD`:  
* **Action:** Жесткая остановка пайплайна (Graceful Shutdown).  
* **Notification:** Email на адрес администратора с темой "BUDGET LIMIT REACHED".  
* **Resume:** Возможность ручного возобновления через API/CLI флаг `--force-resume` или увеличение лимита в конфиге.

#### ***Модуль 2: Session Manager (NEW)***

* **Функция:** Автоматическое управление жизненным циклом сессий.  
* **Логика:**  
* Проверка валидности существующей сессии перед использованием  
* Автоматическое обновление сессии при истечении TTL  
* Автоматическое восстановление после сбоев сессии  
* Кэширование сессий в Redis для переиспользования

#### ***Модуль 3: Ingestion Engine (Обход защиты)***

* **Browser Phase:** Использовать Playwright только для прохождения `__doPostBack` и получения валидных cookies (`ASP.NET_SessionId`).  
* **Network Phase:** Использовать полученные cookies в `httpx` клиенте для скачивания PDF.  
* **Retry Policy (Source Availability):**  
* Если источник возвращает 5xx или Timeouts:  
* Попытка 1 \-\> wait 5m \-\> Попытка 2 \-\> wait 15m \-\> Попытка 3\.  
* Если после 3-й попытки неудача: **Stop Pipeline** и отправка **Email** (текст: "Source GRLS Unreachable").

#### ***Модуль 4: Data Processing (OCR & NLP)***

* **OCR:** Использование Google Gemini Flash с оптимизацией затрат (кэширование, batch processing, fallback на Tesseract).  
* **Validation:** Проверка на "мусорные" данные (если OCR вернул \< 50 символов, считать ошибкой парсинга).

## **6\. Logic: Conflict Resolution & Priority**

Алгоритм обновления записи в БД (`upsert`):

1. **Check:** Существует ли запись с таким `grls_id`?  
* *Нет:* Создать новую (Insert).  
* *Да:* Перейти к шагу 2\.  
2. **Check Lock:** Установлен ли флаг `manual_override = True`?  
* *Да:* **ABORT UPDATE.** Логировать событие "Update skipped due to manual lock" (Level: Info). Обновить только поле `last_sync_attempt`.  
* *Нет:* Перейти к шагу 3\.  
3. **Check Freshness:** Сравнить `hash_sum` нового PDF и старого.  
* *Разные:* Выполнить Update полей `raw_json`, `structured_text`, `hash_sum`.  
* *Одинаковые:* Обновить `last_updated_at`, контент не трогать.

**Улучшение:** Алгоритм остался без изменений, но добавлена более детальная документация процесса логирования.

## **8\. Open Questions / Risks (Mitigation)**

* **Риск:** Изменение структуры `ASP.NET ViewState` на источнике.  
    
* *Mitigation:* При возникновении ошибки `Invalid postback` в логах, пайплайн автоматически сбрасывает сохраненную сессию и инициирует новый "чистый" запуск браузера. Добавлено автоматическое обнаружение изменений верстки через Canary Checks.  
    
* **Риск:** Блокировка IP адресов (WAF).  
    
* *Mitigation:* Поддержка ротации прокси-серверов в конфигурации `httpx` клиента. Автоматическая ротация при обнаружении блокировок.  
    
* **Риск:** Превышение бюджета на OCR.  
    
* *Mitigation:* Реализован Cost Guard с автоматической остановкой при достижении лимита. Добавлено кэширование результатов OCR для снижения затрат.
